# ADR-0001：检索用 BM25 + 向量 + RRF + 重排，而不是单路或加权融合

- 状态：已决定，已用评测验证（默认 `retrieval_mode = hybrid_rerank`）
- 日期：2026-11-02 决定；2026-11-25 评测

## 背景

v4 之前，narrate 拿到的材料是**按位置截断**的：PR / issue 正文取前 4000 字，评论完全不拉。
两个已知问题：PR #6667 的正文恰好在关键处被截断；模型多次说"缺 PR 里的讨论"，而理由常常就在评论里。

v5 改成**按相关性挑选**：把提交说明、PR / issue 正文、全部评论切成段，检索出最相关的 8 段交给 narrate。

查询由三部分组成：目标代码 + 用户问题 + assess 的 `missing`。两种信号混在一起：
- 代码里的标识符（`proxy_bypass_environment`、`ca_cert_dir`、`#6655`）→ 需要精确匹配
- 用户问题和 `missing` 是自然语言，而且常常是**中文**，PR 讨论是英文 → 需要跨语言的语义匹配

## 考虑过的方案

1. **只用向量**：commit message 太短，语义信号稀薄；`#1234`、`FooBar` 这类精确 token 召回差
2. **只用 BM25**：意思相同、用词不同的说法匹配不上；中文问题和英文讨论完全匹配不上
3. **加权融合分数**（`a * bm25_score + b * vec_score`）：两路分数**量纲不同**，
   BM25 是无上界的 tf-idf 累加，余弦相似度在 [-1,1]。归一化方式一换，权重就得重调，
   而且不同 query 的分数分布差异很大
4. **RRF**：只用**排名**不用分数，天然不受量纲影响
5. **RRF + Cross-Encoder 重排**：RRF 之后取前 20 段，用 `BAAI/bge-reranker-base` 把问题和每段拼在一起打分，取前 8 段

## 决定

用方案 5。RRF 公式 `score(d) = Σ 1/(k + rank_i(d))`，k 取 60（原论文的经验值）。

实现细节（都有实测依据，见 `app/rag/`）：
- BM25 用 `BM25Plus`：小语料下 `BM25Okapi` 的 IDF 会变成负数或 0，分不出高低
- 向量用 `intfloat/multilingual-e5-small` + numpy 矩阵乘法。每次只有几十到几百段，不需要向量库；
  e5 要求查询加 `query: `、文档加 `passage: ` 前缀
- 少于 20 字的评论直接丢掉（`:shipit:`、`LGTM` 这类会挤进结果）
- 模型首次加载约 55 秒，服务启动时在后台预热

## 评测

### 方法

评测集 42 条（`evals/dataset.jsonl`），答案用维护者的 `.git-blame-ignore-revs` 和 GitHub 交叉核对构造，见 `evals/README.md`。
其中 36 条在 PR / issue 讨论里能找到"为什么"，为它们标注了（LLM 起草、人工审核，`evals/reasons.json`）：

- 一个中文问题（不含答案）
- 真正的理由和英文原文证据摘录
- 理由在哪：`comments` 20 条、`pr_body` 11 条、`issue` 3 条、`commit` 2 条

每种 `retrieval_mode` 带问题各跑一遍（`python -m evals.run_eval --questions --mode <mode>`），指标：

| 指标 | 含义 | 稳定性 |
|---|---|---|
| 证据进材料 | narrate 收到的材料里有没有证据原文（五种模式都能比） | 高：检索本身是确定的，只有查询里 `missing` 一项由 LLM 生成 |
| 证据 R@5 | 检索前 5 段里有没有证据原文 | 同上 |
| 理由得分 | LLM 评委对照标准理由打 0 / 1 / 2，取平均除以 2 | 低：见下面"噪声" |
| Top-1 | 报告给出的首要关键 PR 是否正确 | — |

### 结果

全部 36 条：

| 模式 | 证据进材料 | 证据 R@5 | 理由得分 | 完全命中 | Top-1 | 每条秒数 |
|---|---|---|---|---|---|---|
| `off`（截断） | 17/36 (47%) | – | 0.76 | 23/36 (64%) | 33/36 (92%) | 36 |
| `bm25` | 25/36 (69%) | 21/36 (58%) | 0.85 | 27/36 (75%) | 34/36 (94%) | 81 * |
| `vector` | 20/36 (56%) | 15/36 (42%) | 0.78 | 22/36 (61%) | 34/36 (94%) | 39 |
| `hybrid` | 25/36 (69%) | 19/36 (53%) | 0.79 | 25/36 (69%) | 34/36 (94%) | 36 |
| **`hybrid_rerank`** | **27/36 (75%)** | **21/36 (58%)** | 0.82 | 25/36 (69%) | 34/36 (94%) | 43 |

\* bm25 是第一个跑的检索模式，耗时含首次拉取评论；之后都走缓存。

理由在评论里（20 条）：

| 模式 | 证据进材料 | 证据 R@5 | 理由得分 |
|---|---|---|---|
| `off` | **1/20 (5%)** | – | 0.62 |
| `bm25` | 13/20 (65%) | 11/20 (55%) | 0.78 |
| `vector` | 11/20 (55%) | 8/20 (40%) | 0.68 |
| `hybrid` | 12/20 (60%) | 10/20 (50%) | 0.70 |
| `hybrid_rerank` | **14/20 (70%)** | **12/20 (60%)** | 0.72 |

理由在 PR 正文里（11 条）：

| 模式 | 证据进材料 | 证据 R@5 | 理由得分 |
|---|---|---|---|
| `off` | **11/11 (100%)** | – | 0.95 |
| `bm25` | 8/11 (73%) | 7/11 (64%) | 0.91 |
| `vector` | 5/11 (45%) | 5/11 (45%) | 0.91 |
| `hybrid` | 9/11 (82%) | 6/11 (55%) | 0.95 |
| `hybrid_rerank` | 9/11 (82%) | 6/11 (55%) | 0.95 |

### 结论

1. **检索的价值在评论**：截断方式不拉评论，理由在评论里的 20 条只有 1 条的证据进了材料；
   `hybrid_rerank` 是 14 条。off 下这些样本的报告大多写"具体原因未找到"——agent 没有编造，只是拿不到证据
2. **两路互补，单用哪一路都不够**：
   - 只有 bm25 找到的 7 条，靠代码标识符对上字面（例：`400 <= r.status_code < 500` ↔ 评论里的 "non-401 response"）
   - 只有 vector 找到的 2 条，问题和评论几乎没有共同的词（例：问"为什么保存成包含 `format` 的字典"，
     评论说 "in preparation for a future where we introduce additional per-file settings"）
   - 查询里代码标识符占大头，所以单用 BM25 比单用向量好，"中文问题必须靠向量"只在少数样本上成立
3. **RRF 单独用没有超过 bm25，重排才把互补性兑现**：
   两路并集 27 条，`hybrid` 只拿到 25 条——只在一路里排第一的段，融合后会被两路都排第 3、第 4 的段挤出前 8。
   `hybrid_rerank` 用 Cross-Encoder 逐段直接判相关性：救回被 RRF 挤掉的 3 条（id 29、35、36），
   另外找到 1 条两路都没找到的（id 21），同时丢了 2 条（id 5、19），25 + 4 − 2 = 27 条
4. **Top-1 测不出检索的差别**：关键 PR 的标题和提交说明本来就在材料里，五种模式都在 92%~94%

### 噪声

agent 和评委用的模型只支持默认温度，每次输出都不同。对比 `bm25` 和 `hybrid`：证据状态完全相同的 32 条里，
有 5 条理由得分不同。所以单次运行的理由得分在 36 条上有约 ±0.05 的波动，**检索模式之间的比较以证据指标为准**；
理由得分只用来看大的差距（例如评论类 off 0.62 → 检索 0.7 以上）。要让它也能用来比较，需要每种模式跑多次取平均。

## 代价

- **丢掉了"位置保证"**：截断方式保证 PR 正文开头一定在材料里；按相关性挑选时，正文开头要和评论竞争 8 个名额。
  理由在 PR 正文里的 11 条，所有检索模式的证据进材料都低于 off（最好 82% vs 100%）。
  改进方向：无论检索结果如何，固定保留 PR 正文第一段
- **RRF 丢掉了分数强弱的信息**：排名第 1 和第 2 差距很大时看不出来；引入了 k 这个超参（实践中不敏感）
- **重排每条多约 7 秒**，模型约 1GB
- **7 条在五种模式下都没找到证据**（id 6、11、28、30、31、32、42），原因待查：证据没进语料、排不进前 8，或标注问题
