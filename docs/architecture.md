# 架构说明

## 为什么需要 Agent，而不是一个脚本

单靠 `git blame` 只能回答"谁在什么时候改的"。要回答"**为什么**"，必须：

1. 从 blame 拿到 commit
2. 从 commit message 里发现它提到了 `#123`
3. 去读 issue #123 的讨论，找到根因描述
4. 发现讨论里又引用了 PR #456
5. 判断信息是否足够——不够就再往上一层

第 5 步是关键：**深挖几层不是固定的，取决于挖到的东西**。这种"边做边判断要不要继续"
的控制流用固定脚本写不出来，需要状态机 + 条件边 + LLM 做判断。

## 状态机

节点职责见 `app/agent/nodes/`。核心是 `assess` 这条条件边：

- 信息足够 → `retrieve` → `narrate`
- 信息不足且未超 `MAX_DEPTH` → 回到 `expand_history`
- 超过 `MAX_DEPTH` 或 token 预算 → 触发 HITL 中断，问用户要不要继续

Checkpoint 用于两处：HITL 中断后恢复；同一 repo 的重复查询复用已建索引。

## 检索为什么必须是 Hybrid

语料是异构的，三种东西的检索特性完全不同：

| 语料 | 特点 | BM25 | 向量 |
|---|---|---|---|
| commit message | 极短，常含 hash、issue 编号、函数名 | **强** | 弱（太短，语义稀薄） |
| issue / PR 讨论 | 很长，口语化，描述"当时遇到什么问题" | 弱 | **强** |
| 代码与注释 | 符号为主，标识符精确匹配重要 | **强** | 中 |

单用任何一种都会在另一类语料上失效，所以用 RRF 融合两路结果。
这是选 Hybrid 的**真实理由**，不是为了技术展示。
